# SharpCpp.Rbfx agent guide

This repository generates C# bindings for the rbfx game engine with SharpCpp. It is an
external SharpCpp consumer: it uses only SharpCpp's public projects, native headers
(`include/SharpCpp`) and CMake modules (`cmake/`).

## Layout

- `SharpCpp.Rbfx.Generator/` - phase-1 generator for the installed rbfx SDK headers.
- `Rbfx.UserCode.Generator/` - the phase-2 user-code generator.
- `SharpCpp.Rbfx.NativeHost/` - native hosting on Android, iOS and web (attach of the managed function table to `SharpCpp.Rbfx.Host`). Only heads reference it. `SharpCpp.Rbfx.Bindings` does not reference it, and the NuGet packages do not contain it.
- `Rbfx.Host/` - native library that hosts the .NET runtime (`SharpCpp::RbfxHost`). Public headers are `Urho3D/CSharp/DotNetHost.h`, and `DotNetHostExport.h` (`namespace Urho3D`). `DotNetHost` is an `Object`: hold it as `SharedPtr<DotNetHost>` and create it with `MakeShared<DotNetHost>(context)`. `DotNetHost::Start(pluginName)` (directory from `SetDirectory`, default `FileSystem::GetProgramDir()`) starts the runtime and loads the plugin, `GetLastError()` has the error text, and `Stop()` closes the host. The default launcher calls them. The API uses the EASTL types of the engine (`ea::string` for paths in UTF-8, `ea::string_view`, `ea::string&` for errors), never `std::string` or `std::filesystem::path`, and the library links `Urho3D`. `DotNetHost::LoadPlugin(PluginManager*, ea::string path, ea::string& error)` loads `SharpCpp.Rbfx.Bindings.dll` into the default load context and calls `NativeHostEntryPoints.LoadPlugin`. Call it after `Engine::Initialize`. `cmake/FindNetHost.cmake` finds nethost. It detects a musl RID on Linux, and `NETHOST_RID` overrides the RID. The nethost linkage follows `BUILD_SHARED_LIBS` (`NETHOST_PREFER_SHARED`). A shared link uses `libnethost.so`, `libnethost.dylib` or `nethost.dll`, and the host build copies it next to the host library. A static link uses `libnethost.a`. MSVC always links the import library `nethost.lib` (the static `libnethost.lib` uses /MT and does not link with /MD). The top-level `CMakeLists.txt` sets `BUILD_SHARED_LIBS` from `RBFX_NATIVE_LIBRARY_TYPE`. The Android toolchains use `c++_shared` unless the command line sets `-DBUILD_SHARED_LIBS=OFF`. `-DRBFX_ANDROID_STL=c++_shared` or `c++_static` overrides both.
- CMake SDK: `RBFX_INSTALL_SDK` (default ON when `RBFX_BUILD_HOST` is ON and the project is top-level) adds install rules. `Rbfx.Host/CMakeLists.txt` installs the host target (export `SharpCppRbfxTargets`, imported name `SharpCpp::RbfxHost` through `EXPORT_NAME`), the two public headers (three in shim mode, with `DotNetHostShim.h`) and the shared nethost library. The root `CMakeLists.txt` writes `SharpCppRbfxConfig.cmake` (from `cmake/SharpCppRbfxConfig.cmake.in`; no version file) and installs `FindNetHost.cmake`, `RbfxCSharpDotNet.cmake`, `RbfxCSharpPlugin.cmake`, `RbfxCSharpLauncher.cmake`, `RbfxCSharpData.cmake`, `RbfxCSharpApplication.cmake` and `RbfxCSharpProject.cmake` to `share/SharpCppRbfx/cmake`. The Config finds `NetHost` only for a static host. `SharpCpp.Rbfx.Bindings/CMakeLists.txt` adds the bindings `SharpCppRbfx_Native` to the same export set (`SharpCpp::RbfxNative`) in a source-mode build with a shared library type. It installs the engine runtime files next to the bindings through `CopyRbfxRuntimeDependencies.cmake.in` (`destination_dir`) and the metadata to `share/SharpCppRbfx/metadata`. The root `CMakeLists.txt` also installs the managed assemblies (`SharpCpp.Rbfx.Bindings`, `SharpCpp.Rbfx.NativeHost`, `SharpCpp.Support`, `SharpCpp.Std`, `SharpCpp.Ea`, `SharpCpp.Rbfx.SourceGenerator`) from `SHARPCPP_MANAGED_OUTPUT_ROOT/<Config>` to `share/SharpCppRbfx/managed`. The Config sets `SharpCppRbfx_MANAGED_DIR` only when this payload is installed. The shim package `cmake/SharpCppRbfx/share/SharpCppRbfx/SharpCppRbfxConfig.cmake` builds this source tree for a consumer with `find_package(SharpCppRbfx)` and sets the same variables. The default output roots are `<repo>/build/bin` for a top-level build and `<build>/SharpCppRbfx/bin` and `<build>/SharpCppRbfx/managed` otherwise. `cmake/RbfxInstallUserCodeGenerator.cmake` (an install script) copies the user-code generator and its dependencies, selected from `Rbfx.UserCode.Generator.deps.json`, to `share/SharpCppRbfx/tools/usercode`. The install step needs no dotnet and does not build: run `dotnet build` first. It installs the `include/SharpCpp` headers of SharpCpp and of this repository (merged), `SharpCppGeneratedStaleness.cmake`, `SharpCppOutput.cmake`, `ExportRbfxSdkParseFlags.cmake`, `RbfxCSharpAddBindings.cmake` with `cmake/templates`, and a copy of the builtin Clang headers (`share/SharpCppRbfx/clang-resource/include`, the link target of `SHARPCPP_CLANG_RESOURCE_DIRECTORY/include`). In a source-mode build with a shared library type (`SHARPCPP_RBFX_SDK_HAS_USERCODE`), the Config sets the inputs of `rbfx_csharp_add_bindings()` to the installed files, writes the SDK flags file from the `Urho3D` target of the consumer, creates `SharpCpp::NativeSupport` and includes the module. The module takes `SHARPCPP_RBFX_SHARPCPP_INCLUDE_DIRECTORY`, `SHARPCPP_RBFX_RBFX_INCLUDE_DIRECTORY` and `SHARPCPP_RBFX_STALENESS_SCRIPT`. The root `CMakeLists.txt` sets them to the source-tree files. The module and `rbfx_csharp_add_plugin_build()` depend on `sharpcpp-generate-rbfx` and `sharpcpp-rbfx-runtime` only when these targets exist. It also installs `cmake/sdk/SharpCppRbfxUserCode.props` and `.targets` (the MSBuild files of the written user-code project in SDK mode: compiler options, generated sources and references to the managed assemblies through `SharpCppRbfxManagedDir`). In the user-code block the Config sets `RBFX_CSHARP_MSBUILD_PROPS`, `RBFX_CSHARP_MSBUILD_TARGETS` and `RBFX_CSHARP_MSBUILD_PROPERTIES` (`SharpCppRbfxIsSdk=true;SharpCppRbfxManagedDir=<managed dir>`) to these files unless the consumer sets them. A package-version SDK defines `rbfx_csharp_add_bindings()` as a stub that stops with an error.
- `Rbfx.Examples/Example.UserCode/` - example (CMake option `RBFX_BUILD_USERCODE`; `RBFX_BUILD_EXAMPLES` builds `Example.NativeHost`; both default to `PROJECT_IS_TOP_LEVEL`, so OFF for a consumer; they are for CI and development, and no `install()` rule and no SDK archive has them): native C++ component (`RotatingComponent`), static `TextTools::RepeatText`, and CMake. The files are directly in the directory. No managed project.
- `Rbfx.Examples/Example.Common/` - shared demo with the native user code `Example.UserCode`. One project with two modes. Source mode (default) references the bindings source projects. Package mode (`-p:RbfxBindingsPackageVersion=VERSION`) references the `SharpCpp.Rbfx.Bindings` package. `Example.Desktop`, `Example.Android`, `Example.Ios`, `Example.Wasm` and `Example.Uwp` use it.
- `Rbfx.Examples/Example.NativeHost/` - example: C++ rbfx `Application` that hosts .NET. `DotNetHost::LoadPlugin` loads a C# `ManagedPlugin`, and C++ creates its `LogicComponent` by name with `CreateComponent("Spinner")`. The managed entry point of `LoadPlugin` is `Urho3D.Plugins.NativeHostEntryPoints` in `SharpCpp.Rbfx.Bindings`.
- `SharpCpp.Rbfx.Bindings/` - generated rbfx bindings assembly and hand-written runtime glue.
- `SharpCpp.Ea/`, `SharpCpp.Rbfx.SourceGenerator/` - EASTL containers and Roslyn helpers.
- `SharpCpp.Rbfx.Tests.E2E/` - round-trip tests against the generated rbfx bindings.
- `include/SharpCpp/detail/Rbfx*.hpp` - rbfx marshaller configuration headers.
- `native/SharpCpp.Rbfx.Native/` - MSBuild project that drives the CMake native build.
- `cmake/RbfxCSharpEditor.cmake`, `cmake/launcher/RbfxCSharpEditor.cpp` and `SharpCpp.Rbfx.EditorHost/` - the editor target `rbfx_csharp_add_editor()` (desktop only, skipped without `EditorLibrary`). The bootstrap plugin registers `ManagedPlugins/*.dll` of the editor folder.
- `packaging/nuget/` - NuGet packaging for the generated bindings.

## Inputs

- `SharpCppRoot` (MSBuild) / `SHARPCPP_ROOT` (CMake): SharpCpp checkout; defaults to the
  sibling `../SharpCpp`.
- `RbfxSdkRoot` (MSBuild) / `CMAKE_PREFIX_PATH` (CMake or environment): installed
  shared-library rbfx SDK. CMake finds the engine only with `find_package(Urho3D)` through
  `CMAKE_PREFIX_PATH`. `cmake/RbfxEngineLayout.cmake` sets `RBFX_ENGINE_ROOT` and selects one of two modes.
  Installed SDK mode: the `Urho3D` target is IMPORTED. `RBFX_ENGINE_ROOT` comes from `Urho3D_DIR`, and the generator gets `--sdk-root`.
  Source engine mode: the `Urho3D` target is not IMPORTED. `RBFX_ENGINE_ROOT` is the rbfx checkout, and the generator gets
  `--engine-header-root <Name>=<dir>` and `--engine-header-list <file>` (the headers that the `Urho3D` target compiles).
  MSBuild takes `RbfxSdkRoot` (default: the environment variable `CMAKE_PREFIX_PATH`, then
  `build/sdk/<rid>`, then `../../rbfx-sdk`) and passes it to CMake as `CMAKE_PREFIX_PATH`.

## Wrap user C++ code

`rbfx_csharp_add_bindings(<target> HEADERS ... [INCLUDE_DIRECTORIES IMPLEMENTATION NAMESPACE
ASSEMBLY_NAME BINDINGS_CLASS LIBRARY_NAME SYMBOL_PREFIX GENERATED_DIRECTORY LIBRARY_TYPE CSPROJ SEPARATE_LIBRARY])` is in
`cmake/RbfxCSharpAddBindings.cmake`.
Integration mode (default with one `IMPLEMENTATION` target): the generated `.g.cpp` is added to that target with
`target_sources` (plus `cxx_std_20`, the include directories, `SharpCpp::NativeSupport` and a dependency on
`sharpcpp-generate-<target>`), and `<target>` is an `INTERFACE` library with the bindings properties. The generator parses only
headers, so it does not wait for the build of the implementation and there is no cycle. The C# import name is the `OUTPUT_NAME` of
the implementation target (or its name), so set `OUTPUT_NAME` before the call. `LIBRARY_NAME` and `LIBRARY_TYPE` are errors in
this mode. A static or object implementation needs `RBFX_NATIVE_LIBRARY_TYPE` STATIC (import name `__Internal`). The exports use
`SHARPCPP_EXPORT` (visibility default). The managed project does not check the native path
(`RbfxConsumedNativeLibraryPath` is empty). A `RbfxUserCodeReference` in an MSBuild project looks for
`$(SharpCppOutputDir)/lib<LibraryName>.so`, so for an integration bindings target set the metadata `LibraryName` to the output name of
the implementation target and build that target into the native output root. `SEPARATE_LIBRARY` (or no `IMPLEMENTATION`) makes a
native library `<LIBRARY_NAME>` (default `<target>.Native`) with the glue, as before. The implementation target must use the keyword signature of `target_link_libraries`, and an object library works only on Emscripten (a fatal error otherwise; the iOS head needs `$<TARGET_FILE:>`). `rbfx_csharp_add_project` has the option `SEPARATE_LIBRARY` and passes it on. The property `SHARPCPP_RBFX_NATIVE_TARGET` of
the bindings target names the target with the native code; `rbfx_csharp_bindings_native_target(<bindings> <out>)` reads it, and the
packaging, install and head code use it (the plugin `REFERENCES` stay the bindings targets).

- The function creates only the bindings target: the generator target `sharpcpp-generate-<target>`, the native library `<target>` with the generated bindings, and the managed project files. It has no `SOURCES`. The implementation of the headers is a separate target. The caller passes it in `IMPLEMENTATION` (linked PUBLIC). `Example.UserCode.Impl` is the example. It is a static library (an object library when the native libraries are static).
- At configure time it writes `Directory.Build.props`, `Directory.Build.targets`, `<target>.props`
  and `<ASSEMBLY_NAME>.csproj` into the build tree, below `usercode/<target>/`.
- The user needs no generator knowledge and no bindings csproj.
- One driver builds the native tree. MSBuild is the driver when it builds `SharpCpp.Rbfx.slnx`: target `RbfxBuildNative` of `native/SharpCpp.Rbfx.Native` runs `BuildNative.cmake` under a lock and configures with `-DRBFX_CSHARP_BUILD_MANAGED=OFF`. CMake is the driver when it builds the tree. Then CMake runs `dotnet build` only through `rbfx_csharp_add_dotnet_project()` and `rbfx_csharp_add_plugin_build()` (`cmake/RbfxCSharpDotNet.cmake`). These pass `-p:RbfxNativeBuildDriver=cmake -p:RbfxNativeBuildDir=<CMake binary dir>`, so `RbfxBuildNative` does not run in the nested build. A nested MSBuild that runs `RbfxBuildNative` would wait on the lock or start a second build of the same tree. The option `RBFX_CSHARP_BUILD_MANAGED` (default ON) turns the managed targets off. Do not set the driver rule aside. The driving build system defines the configuration set of the driven one. MSBuild keeps `Debug;Release` (`Configurations` in `eng/SharpCpp.Rbfx.Build.props`) and runs CMake with `--config $(Configuration)`. CMake passes `-c $<CONFIG> -p:Configurations=<list>` (helper `rbfx_csharp_msbuild_configuration_arguments()` in `cmake/RbfxCSharpDotNet.cmake`; the list is `CMAKE_CONFIGURATION_TYPES`, else `CMAKE_BUILD_TYPE`, else Release). So `$(Configuration)` names the native library folder on both sides. Each configuration other than Debug builds like Release (`Optimize`, `RELEASE`), and the Android and Wasm head projects map it to the Release defaults of their workload (Android: Mono AOT on MonoVM, ReadyToRun only with `UseMonoRuntime=false`).
- A consumer tree (add_subdirectory or the find_package shim) builds the generators itself: the option `RBFX_CSHARP_BUILD_GENERATORS` (default ON when the project is not top-level, OFF otherwise; it needs `RBFX_CSHARP_BUILD_MANAGED`) adds the targets `sharpcpp-rbfx-build-generator` and `sharpcpp-rbfx-build-usercode-generator`. They run `dotnet build` into `SHARPCPP_MANAGED_OUTPUT_ROOT/<Config>` with the intermediate files in `<build>/SharpCppRbfx/dotnet`. `sharpcpp-generate-rbfx` and the user-code generate targets depend on them. The target `sharpcpp-rbfx-build-managed` builds `SharpCpp.Rbfx.Bindings` (and its references Std, Ea, Support) after the native bindings, so `SharpCppRbfx_MANAGED_DIR` holds them. In a consumer tree the root sets `RBFX_CSHARP_MSBUILD_PROPERTIES` (`SharpCppManagedOutputRoot`, `SharpCppNativeOutputRoot`, `SharpCppBuildRoot`). `rbfx_csharp_add_dotnet_project()` passes them as `-p:` and the written user-code `Directory.Build.props` sets them, so every dotnet build uses the same roots. The shim copies the variables that `rbfx_csharp_add_bindings()` reads (the global property `SHARPCPP_RBFX_USERCODE_INPUT_VARIABLES` in `cmake/RbfxCSharpAddBindings.cmake`, which the function checks too) to the consumer scope. MSBuild sets `RBFX_CSHARP_BUILD_MANAGED=OFF`, so the MSBuild path is unchanged. A CMake-driven build needs the generators in `build/bin/<Config>` (`SharpCpp.Rbfx.Generator.dll`, `Rbfx.UserCode.Generator.dll`) first. Run `dotnet build SharpCpp.Rbfx.slnx` once. Do not use the tree `build/native/linux-gcc-x64-dll` for both drivers: `BuildNative.cmake` configures it again with `RBFX_CSHARP_BUILD_MANAGED=OFF`. Use another binary directory for a CMake-driven build, or configure with `-DRBFX_CSHARP_BUILD_MANAGED=ON` again.
- CMake presets follow the rbfx scheme `<platform>-<compiler>-<arch>-<dll|lib>`. Build presets add `-debug` or `-release`. Host presets (`linux-gcc-x64-dll`, `macos-clang-arm64-dll`, `windows-msvc-x64-dll`) have a host condition and the binary directory `build/native/<preset>`. Cross presets use `build/cross/<preset>`. `eng/SharpCpp.Rbfx.Build.props` holds the one map from RID to preset (property `RbfxNativePreset`): `linux-x64` to `linux-gcc-x64-dll`, `osx-arm64` to `macos-clang-arm64-dll`, `win-x64` to `windows-msvc-x64-dll`, `android-arm`, `android-arm64` and `android-x64` to `android-clang-<arch>-dll`, `ios-arm64` to `ios-clang-arm64-lib`, `browser-wasm` to `web-emscripten-wasm-lib`, `uap-x64` to `uwp-msvc-x64-dll`. `-p:RbfxNativePreset=<name>` overrides the map. The toolchain files in `cmake/toolchains` keep their RID names. The preset `ios-clang-arm64-lib` has no toolchain file. It sets `PLATFORM` and `DEPLOYMENT_TARGET` for the toolchain file `share/Urho3D/CMake/Toolchains/IOS.cmake` of the engine SDK. `eng/SharpCpp.Rbfx.Build.props` passes that file as `CMAKE_TOOLCHAIN_FILE` from `RbfxSdkRoot`. A manual `cmake --preset ios-clang-arm64-lib` needs `-DCMAKE_TOOLCHAIN_FILE=<engine SDK>/share/Urho3D/CMake/Toolchains/IOS.cmake`.
- `CSPROJ <path>`: the user supplies the project and the function writes none. `<target>.props` stays available to import.
- Opt-in hooks: a user csproj can import `<target>.props`. Cache variables are
  `RBFX_CSHARP_BINDINGS_PROJECTS`, `RBFX_CSHARP_BINDINGS_PACKAGE_VERSION`,
  `RBFX_CSHARP_MSBUILD_PROPS` and `RBFX_CSHARP_MSBUILD_TARGETS`. Target properties are
  `SHARPCPP_RBFX_MANAGED_PROJECT`, `SHARPCPP_RBFX_MANAGED_PROPS` and `SHARPCPP_RBFX_MANAGED_ASSEMBLY`.
- A duplicate `ASSEMBLY_NAME` is a configure error.

A consumer csproj declares `<RbfxUserCodeReference Include="<cmake target>" />`.
`eng/SharpCpp.Rbfx.Build.targets` then adds a reference to the native project. Target
`RbfxResolveUserCodeReferences` restores and builds the generated project and references its dll.
So the wrapped user code gives a dll that other modules use.

`eng/SharpCpp.Rbfx.NativeItems.targets` is the one mapping from a RID to the platform items for native libraries (Android `AndroidNativeLibraryNoJniPreload` for every `*.so`, iOS `NativeReference`, Wasm `NativeFileReference` and `--js-library` flags). Its input is the `RbfxNativeRuntimeFile` items with the metadata `RbfxNativeRid` and `RbfxNativeKind`. It maps only the items of the RID of the consumer (`RbfxTargetRid`, else `RuntimeIdentifier`) and is idempotent. `eng/SharpCpp.Rbfx.Build.targets` imports it. `packaging/nuget/CrossPackage.cs targets` lists the staged files as `RbfxNativeRuntimeFile` and copies the shared file to `buildTransitive/SharpCpp.Rbfx.NativeItems.<rid>.targets` of the runtime package.

## Application heads

`rbfx_csharp_package_application(<launcher> PLUGIN <plugin> [DATA <data>] [RESOURCES] [APPLICATION_ID] [HEAD_SOURCES] [PROPERTIES])` (`cmake/RbfxCSharpApplication.cmake`) packages a launcher with a plugin and data: on desktop the plugin build and copy targets, on Android, iOS and
Emscripten a .NET head from the templates in `cmake/heads/<platform>/`. It must be called in the source folder of the launcher (`SOURCE_DIR` of the launcher equals `CMAKE_CURRENT_SOURCE_DIR`, else a fatal error), because it uses `cmake_language(DEFER DIRECTORY)`. It defines `SHARPCPP_RBFX_PLUGIN_NAME` for the launcher, reads the bindings targets from `SHARPCPP_RBFX_PLUGIN_REFERENCES` of the plugin and the native plugins from `SHARPCPP_RBFX_PLUGINS` of the launcher, and sets `SHARPCPP_RBFX_PACKAGED_PLUGIN`, `SHARPCPP_RBFX_PACKAGED_DATA` and `SHARPCPP_RBFX_APPLICATION_OUTPUT` on the launcher. `PROPERTIES` is appended to `SHARPCPP_RBFX_PLUGIN_MSBUILD_PROPERTIES` of the plugin for the dotnet build. `RESOURCES` files get the target `<launcher>.Resources` (no deferral), the paks of `DATA` come with the data target. `HEAD_SOURCES` (C# files, absolute or relative to the current folder) become `<Compile>` items through `RBFX_HEAD_SOURCES_ITEMS` in every head template. Each head declares `internal static partial class Program` with the partial hooks `OnManagedStartup` and `OnManagedShutdown` (only desktop calls `OnManagedShutdown`; on Android `RbfxApplication.OnCreate` calls `Program.RunStartup()`), so one file compiles on every platform, and each head project has the SharpCpp.Rbfx source generator as an analyzer, so the head assembly gets its own type registry. README.md describes each platform. On Emscripten the launcher calls `web_executable` of the engine. Its link options reach the head through `_rbfx_csharp_collect_native_link_items`. The host library compiles with `-pthread` (PUBLIC), because wasm-ld needs atomics in every object file.

- The plugin project: `rbfx_csharp_add_plugin(<plugin> [CSHARP_DIR] [CSPROJ] [REFERENCES] [PROPERTIES])` (`cmake/RbfxCSharpPlugin.cmake`) makes the utility target `<plugin>` (the target name is the assembly name). `rbfx_csharp_add_project` calls it with the plugin name `<name>.Net` (or the file name of `CSPROJ`) and passes `<name>.Bindings` and the `BINDINGS_TARGETS` targets as `REFERENCES`. It sets `SHARPCPP_RBFX_PLUGIN_NAME`, `SHARPCPP_RBFX_PLUGIN_PROJECT`, `SHARPCPP_RBFX_PLUGIN_REFERENCES` and `SHARPCPP_RBFX_PLUGIN_MSBUILD_PROPERTIES` (the MSBuild properties of the package, then `PROPERTIES`). `rbfx_csharp_package_application` reads them back (`plugin_project`, `plugin_properties`, `arg_BINDINGS_TARGETS`). It does not build the plugin: `rbfx_csharp_add_plugin_build` does that in the desktop branch, and the heads reference the project. Without `CSPROJ` the function writes `<build>/csharp/<plugin>/<plugin>.csproj` from `cmake/templates/Plugin.csproj.in`. It always writes `SharpCppRbfx.Plugin.props` from `cmake/templates/Plugin.props.in`. That file imports `cmake/sdk/SharpCppRbfxPlugin.props`. The MSBuild property `SharpCppRbfxPluginProps` is its path. A user `CSPROJ` imports it. The heads use the resolved project path (`plugin_project`).
- The launcher: `rbfx_csharp_add_launcher(<name> [SOURCES] [PLUGINS] [LINK_LIBRARIES] [CONSOLE])` (`cmake/RbfxCSharpLauncher.cmake`) makes the native target of the platform (executable, Android shared library, web object library with `web_executable` and `RbfxWebMain.cpp`, iOS static library with `RbfxIosMain.cpp`), links the host library and calls `target_link_plugins`. It sets `SHARPCPP_RBFX_LAUNCHER`, `SHARPCPP_RBFX_PLUGINS` and the internal property `SHARPCPP_RBFX_LAUNCHER_LINK_LIBRARIES` (the Android head packs the shared libraries from it, with `PlayerLibrary` of the default launcher). It does not know the plugin. `rbfx_csharp_package_application` defines `SHARPCPP_RBFX_PLUGIN_NAME` and adds the plugin build, the heads and the resources. The platform functions of the application create no launcher target.
- The data: `rbfx_csharp_add_data(<data> [DIRECTORIES] [NO_CORE_DATA])` (`cmake/RbfxCSharpData.cmake`, installed and included like the other modules: root `CMakeLists.txt`, `SharpCppRbfxConfig.cmake.in`) makes the target `<data>` in the folder of the call. CoreData (`rbfx_csharp_find_core_data`) is the first folder unless `NO_CORE_DATA`. On Emscripten, Android and iOS it calls `create_pak` for each folder (`<build>/<data>.Resources/<folder>.pak`) and the target depends on the paks (the custom commands belong to the folder of the call, so the target must be there). On desktop it writes `<build>/<data>.Install/ResourceRoot.ini` with `file(GENERATE)`. Properties: `SHARPCPP_RBFX_DATA_DIRECTORIES` and `SHARPCPP_RBFX_DATA_FILES` (paks, or the ini file on desktop). A duplicate folder name is a fatal error, a missing CoreData is a fatal error on the pak platforms only.
- `SOURCES` is optional. Without it the launcher uses `cmake/launcher/RbfxCSharpLauncher.cpp` and adds `PlayerLibrary` to `LINK_LIBRARIES` (a fatal error if the target does not exist). The launcher uses `DotNetHost::Start()` of `Urho3D/CSharp/DotNetHost.h`, `LinkedPlugins::GetLinkedPlugins()` and the compile definition `SHARPCPP_RBFX_PLUGIN_NAME`. The root `CMakeLists.txt` installs `cmake/launcher` next to `cmake/templates`. Without `PLUGINS` the default launcher still gets an empty `target_link_plugins` call, because it needs `LinkedPlugins.cpp`.
- `PLUGINS` is a list of native plugin targets. `rbfx_csharp_add_launcher` calls `target_link_plugins(<name> "<PLUGINS>")` (the list is one quoted argument, because the function has one list parameter). Desktop: the `<name>.Native` target copies each shared bindings library to the folder of the executable. Android: `libraries` and `library_targets` get the shared and module `PLUGINS` targets and then the shared bindings targets, without duplicates, before `lib<name>.so`.
- Each platform function sets the target property `SHARPCPP_RBFX_APPLICATION_OUTPUT` (Android `<LIBRARY_OUTPUT_DIRECTORY>/<name>.apk`, web the web folder, iOS `<runtime dir>/<name>.app`, desktop empty).
- The dispatch is in `rbfx_csharp_add_launcher` (the target) and `rbfx_csharp_package_application` (the head): `ANDROID`, `EMSCRIPTEN`, then `CMAKE_SYSTEM_NAME` `iOS`. tvOS and visionOS are a configure error of the launcher.
- `cmake/RbfxCSharpProject.cmake` (installed with the other modules, included by the root `CMakeLists.txt` and by `SharpCppRbfxConfig.cmake.in`) has three functions. `rbfx_csharp_add_project` resolves the relative paths against `CMAKE_CURRENT_SOURCE_DIR`, calls `rbfx_csharp_add_bindings(<name>.Bindings)` when `HEADERS` is set (a fatal error if the command does not exist), then, with `BINDINGS_TARGETS` (existing bindings targets, for example of other plugins; a fatal error for a non-target), adds them after `<name>.Bindings` to the `REFERENCES` of the plugin, then `rbfx_csharp_add_plugin`, `rbfx_csharp_add_launcher`, `rbfx_csharp_add_data(<name>.Data)` (always, with `DATA` as `DIRECTORIES`) and `rbfx_csharp_package_application`, and then, with `INSTALL`, `rbfx_csharp_install_application`. `rbfx_csharp_install_application` reads the launcher properties `SHARPCPP_RBFX_PACKAGED_PLUGIN`, `SHARPCPP_RBFX_PACKAGED_DATA`, `SHARPCPP_RBFX_APPLICATION_OUTPUT` and `SHARPCPP_RBFX_PLUGINS`, and from the plugin `SHARPCPP_RBFX_PLUGIN_NAME` and `SHARPCPP_RBFX_PLUGIN_REFERENCES` (it is a fatal error without the first and the third). On desktop it installs the executable, the engine library `Urho3D` (when its type is `SHARED_LIBRARY`), `SharpCpp::RbfxNative`, the shared host with the shared nethost library (next to the host library), the shared bindings and native plugin libraries, and the managed files of the executable folder (`<plugin>.*`, `SharpCpp.*.dll`, `<bindings assembly>.*`). It also installs each folder of the data target (`SHARPCPP_RBFX_DATA_DIRECTORIES`, CoreData first) and its files (`SHARPCPP_RBFX_DATA_FILES`: the generated `ResourceRoot.ini` with one `<folder>=<folder>` line for each folder). The executable gets `INSTALL_RPATH` `$ORIGIN` (`@loader_path` on Apple). `rbfx_csharp_find_core_data` returns `${Urho3D_PACKAGE_ROOT}/bin/CoreData`, else `bin/CoreData` of a `CMAKE_PREFIX_PATH` folder, else `<out_var>-NOTFOUND`.
- `cmake/RbfxCSharpNewProject.cmake` (usage `cmake -DNAME=<Name> -DDESTINATION=<dir> -P RbfxCSharpNewProject.cmake`) makes a project from `cmake/project/`. `NAME` must match `^[A-Za-z][A-Za-z0-9_]*$`. `DESTINATION` must be missing or empty (a fatal error otherwise). Each `*.in` goes through `configure_file(@ONLY)` without the suffix, and `CSharp/Plugin.cs` becomes `CSharp/<Name>Plugin.cs`. The script finds the templates with `CMAKE_CURRENT_LIST_DIR`, so it works from the source tree and from the installed module folder. The root `CMakeLists.txt` installs the script and `cmake/project` with `cmake/templates`. The template `CMakeLists.txt.in` writes `<build>/ResourceRoot.ini` (CoreData from `rbfx_csharp_find_core_data`), because the engine uses the first `ResourceRoot.ini` above the executable. Keep the templates free of other `@...@` text.
- iOS (`_rbfx_csharp_add_ios_application`): the static library `<name>` (SOURCES and `cmake/heads/ios/RbfxIosMain.cpp`), the head
  `<build>/heads/<name>/<name>.Head.csproj` (`net10.0-ios`, `ios-arm64`) and the deferred `NativeItems.props` (`NativeReference` items).
  `Program.cs` attaches the native host and calls `rbfx_application_start`. That function calls `SDL_UIKitRunApp` with the `SDL_main` of `URHO3D_DEFINE_APPLICATION_MAIN`.
- Only the application library, the bindings, the host library and the libraries of the bindings targets have `ForceLoad`. The engine archive has the `main` of SDL. A force load of it gives a second `main`.
- Desktop in shim mode (`_rbfx_csharp_add_desktop_shim_application`): `dotnet publish` of the NativeAOT head `<build>/heads/<name>/<name>.Head.csproj` (`cmake/heads/desktop/`), copied next to the executable as `<plugin>.Head<suffix>` (no `lib` prefix). `_rbfx_csharp_add_desktop_native_copy` makes `<name>.Native` for both desktop modes. Test: `eng/run-aot-test.sh --rid linux-x64` (`SharpCpp.Rbfx.Tests.Aot/`).
- The heads write their own native items. They do not import `eng/SharpCpp.Rbfx.NativeItems.targets`. Keep the iOS frameworks and the flags `-lc++ -liconv` in `_rbfx_csharp_write_ios_native_items` the same as for the bindings in that file.
- `_rbfx_csharp_collect_native_link_items` walks the link closure for the wasm and the iOS heads.
- Verification of the iOS head on Linux: configure a project that calls the function with fake imported static targets, a toolchain with
  `CMAKE_SYSTEM_NAME` `iOS`, `CMAKE_OSX_SYSROOT` in a folder with the name `iPhoneOS.sdk` and `CMAKE_CXX_COMPILER_FORCED`. Then check the generated XML with `xmllint`.
  A real head build needs macOS, Xcode and the `ios` workload.

## Run the examples

- `Example.Desktop`, `Example.Common` and the mobile and UWP apps need the native build of `Example.UserCode` (about 7 minutes the first time). Source mode needs `CMAKE_PREFIX_PATH` (the installed rbfx SDK). Package mode (`-p:RbfxBindingsPackageVersion=VERSION -p:RbfxPackageVersion=VERSION`) restores the packages of that version, and the engine natives come from the runtime package.
- `Rbfx.Examples.slnx` also needs the SDK now.
- A Linux desktop run needs `GLIBC_TUNABLES=glibc.rtld.optional_static_tls=32768`.

Do not use absolute paths. Missing generator capabilities are fixed in SharpCpp, not
worked around here.

## Build and verify

```sh
dotnet build SharpCpp.Rbfx.slnx --configuration Debug -maxcpucount
dotnet test SharpCpp.Rbfx.Tests.E2E --configuration Debug --no-build --no-restore
```

Fetch a prebuilt rbfx SDK with `eng/fetch-rbfx-sdk.sh --rid <rid>` (default: the host RID).
It needs `curl`, `jq` and `7z`. It extracts the SDK into `build/sdk/<rid>` and does nothing if the
SDK is current. Set `CMAKE_PREFIX_PATH="$(eng/fetch-rbfx-sdk.sh --rid linux-x64 --print-root)"` before
CMake or MSBuild. `--print-cache-key` prints the CI cache key. `browser-wasm` comes from the
SharpCpp.Rbfx release `latest`. See `--help` for all options.

Set the MSBuild property `RbfxBindingsPackageVersion` to build the user code against the built
packages (from package.sh or CI, in a local feed). It adds `-DRBFX_CSHARP_BINDINGS_PACKAGE_VERSION=<version>` and `-DRBFX_BUILD_HOST=OFF` to
`RbfxNativeConfigureArguments`. The generated bindings project then references the package
`SharpCpp.Rbfx.Bindings`. The native build neither runs the engine generator nor compiles `SharpCppRbfx_Native`. The user-code generator reads the engine
binding metadata from the runtime package (`runtimes/<rid>/metadata/SharpCpp.Rbfx.Bindings.json`, with the umbrella header `SharpCpp.Rbfx.ParseUmbrella.hpp` that the user bindings includes). The consumer project finds the file in the restored package
folder (`eng/SharpCpp.Rbfx.Build.targets`, target `RbfxSetProjectReferenceProperties`) and passes it through the native project to `-DRBFX_ENGINE_METADATA_FILE`.
Restore the consumer first. Unset means source build.

Plugin class: `PluginRuntime.FindPluginType` reads `PluginModuleAttribute`, else the `GeneratedPluginTypeAttribute` that `TrimRootsGenerator` emits for the first concrete `Plugin` class with a public constructor that takes a `Context` (by documentation id). It never calls `GetTypes`. An assembly without the generator needs `PluginModule`. There is no `RegisterFactory(Type, ...)` overload: use `RegisterFactory<T>`.

Managed types and attributes: the generated registry (`SharpCpp.Rbfx.SourceGenerator`) is the only path. There is no reflection scan and no `GetManagedTypes`. Each plugin and head project must reference the generator and `SharpCpp.Support.SourceGenerator` (from the SharpCpp checkout). In the source tree, `Directory.Build.targets` adds both as analyzers to each project with a `ProjectReference` to `SharpCpp.Rbfx.Bindings` (a project that lists one keeps it). `SharpCpp.Rbfx.Bindings`, the head templates and `cmake/sdk/SharpCppRbfxPlugin.props` stay explicit. The target `RbfxCheckSourceGenerators` fails the build with SCPPSG002 if a project that uses Bindings has no generator in `@(Analyzer)`. Set `SharpCppRbfxSkipGeneratorCheck=true` in a project with no generator on purpose (`NoRegistryPlugin`, `SharpCpp.Rbfx.NativeHost`); the rule and the check skip it. The second generator emits `IsManagedOverride`, so a class that overrides a native virtual method must be `partial`. A plugin without a registry fails to register with an `InvalidOperationException`, and `Load` logs an error. The generator reports RBFXSG003 and RBFXSG004 as errors for what it cannot describe. Private and protected `[SerializeField]` members use `[UnsafeAccessor]` accessors in the registry file. Keep the `DynamicallyAccessedMembers` annotations on registered types, because head assemblies are not trimmer roots. The heads have no `TrimmerRootAssembly` items. The NativeAOT compiler roots a whole assembly for each item (only `RootMode="EntryPoint"` is no root). `TrimRootsGenerator` writes `SharpCpp.Rbfx.Generated.TrimRoots.Keep` with `[DynamicDependency]` roots for what only native code reaches: concrete `Plugin` classes, `[UnmanagedCallersOnly]` methods without an address-of use, and `Keep` of the referenced assemblies. `Program.cs` of each head keeps `Keep` of the head. Native code that calls a managed method by name needs an `[UnmanagedCallersOnly]` method in an assembly with the generator. Run `eng/run-aot-test.sh` after a change of the roots.

Coherent local commits after validation are authorized; publishing requires explicit
task authorization.
